# Gap Analysis: соответствие проекта требованиям capstone

Дата проверки: 2026-05-18

## Краткий вердикт
Проект **хорошо покрывает техническое ядро** сценария *Financial News Analyst* (multi-agent + RAG + MCP + базовые guardrails + тесты), но **в текущем виде не закрывает часть обязательных deliverables и non-functional требований**, необходимых для полной сдачи по описанию задания.

## Что уже соответствует

### 1) Use-case и архитектурная идея
- Реализован финансовый аналитический use-case с разделением ролей агентов:
  - `MarketDataAgent` (рыночные/профильные данные)
  - `NewsAgent` (новости)
  - `RiskAgent` (риски)
  - `AnalysisAgent` (финальная аналитика)
- Есть оркестрация через `FinancialNewsOrchestrator` и связка с RAG-хранилищем.

### 2) MCP + внешние данные
- Подключен MCP-клиент и описаны используемые инструменты (`web_data_yahoo_finance_business`, `search_engine`, `search_engine_batch`).
- В README задокументированы переменные окружения и схема подключения.

### 3) RAG-слой
- Есть хранение чанков знаний в PostgreSQL, provenance-поля, dedup и fallback-логика retrieval.
- Явно соблюдено правило: финальные LLM-рекомендации не сохраняются обратно в базу знаний.

### 4) Безопасность (базовый уровень)
- Валидация роли/ввода, rate limit, PII masking, prompt-injection blocklist, audit trail.

### 5) Тесты
- Наличие unit/integration тестов по агентам, оркестратору, контроллеру и сервисам политики/лимитов.
- Это закрывает часть требования по позитивным/негативным сценариям поведения.

## Что не закрыто / требует доработки для сдачи

### A. Обязательные deliverables (критично)
В репозитории сейчас отсутствуют явные артефакты, которые комиссия ожидает увидеть как отдельные документы:
1. **Executive Summary (1-2 стр.)**
2. **Architecture Blueprint** (отдельный структурированный документ с обоснованием выбора)
3. **Self-Review** (комментарии по архитектурным решениям и trade-offs)
4. **Ссылка на Video Demo (2-5 мин)**
5. **Файл отправки** `Capstone_project_[name]_[last_name].txt` с email + ссылкой на repo + ссылкой на видео

> Сейчас часть материала есть в README, но формально этого недостаточно, если проверка идет по списку deliverables.

### B. Видео-демо критерии
- Требуется демонстрация:
  - live run системы,
  - запуск positive + negative тестов,
  - self-review с комментариями к коду.
- В репозитории нет ссылки/секции с подтверждением, что видео подготовлено.

### C. Observability & Monitoring (частично)
Есть метрики/аудит, но не видно полного покрытия требований:
- LLM tracing (детальная трассировка взаимодействий/токенов/качества)
- resource usage (CPU/memory/API quota) как явный слой мониторинга
- user feedback/rating механизм

### D. RAG Quality Assurance (частично)
Есть source attribution в ответе и RAG-пайплайн, но не представлены как формальная QA-система:
- retrieval precision/recall метрики
- answer relevance/factual correctness measurement
- hallucination detection pipeline
- bias assessment

### E. Security & Compliance (частично)
Базовые guardrails есть, но обычно для полного зачета не хватает:
- явной аутентификации/авторизации (role в запросе не равно auth-механизм)
- контент-фильтрации как отдельного политики/слоя
- consent management
- формализованных compliance-процедур

### F. Cost & Resource Management (частично)
Плюсы: локальный docker-compose, кэш, PostgreSQL/Redis.
Пробелы:
- явные лимиты/квоты и отчеты по стоимости вызовов LLM
- политика хранения/retention как оформленный документ/конфиг
- сценарии масштабирования и тесты конкурентной нагрузки

## Оценка соответствия (ориентировочно)
- **Base Requirements (70 pts):** вероятно **частично выполнены**.
  - Техническая система и код: ближе к выполнению.
  - Формальные deliverables и видео: пока блокер для полного pass.
- **Excellence bonuses (30 pts):** потенциал есть, но нужны дополнительные артефакты (UX polish, data quality evidence, engineering rationale).

## Рекомендованный минимальный план, чтобы пройти по формальным критериям
1. Добавить документы:
   - `docs/Executive_Summary.md`
   - `docs/Architecture_Blueprint.md`
   - `docs/Self_Review.md`
2. Добавить `docs/Video_Demo.md` со ссылкой на 2-5 мин видео и чеклистом того, что показано.
3. Добавить шаблон/финальный файл:
   - `Capstone_project_[your_name]_[your_last_name].txt`
4. Расширить тест-сет:
   - отдельные негативные/adversarial сценарии с явной маркировкой.
5. Документировать observability и QA-метрики:
   - tracing, latency/success metrics,
   - retrieval quality и hallucination checks.

## Итог
С инженерной точки зрения проект уже близок к нужному use-case. Главный риск сейчас — **не техническое ядро, а неполный пакет обязательных артефактов для сдачи**. После добавления перечисленных документов и видео-подтверждения проект будет существенно ближе к требованиям комиссии.
